# 内存管理学习记录

本文保存从固件给出的内存事实到分页之间的心智模型和设计取舍。当前稳定接口见 [DTB 与启动内存布局模块](../modules/dtb-memory.md) 和 [物理页分配模块](../modules/physical-pages.md)；本文不重复函数清单。

## 启动时的内存信息怎样流动？

当前 RISC-V 路径是：

```text
OpenSBI 的 a1
    -> DTB 地址
    -> dtb_boot_info（RAM、静态保留区、DTB 大小）
    -> boot_memory_layout（再排除固件、内核镜像和 DTB 自身）
    -> physical_page_allocator（只保留完整物理页）
    -> 页表页与被映射的物理页
    -> satp / Sv39（尚未实现）
```

这条链分成四种不同责任：DTB 读取是在发现平台事实；启动内存布局是在做字节区间的排序、合并和相减；物理页分配是在管理可复用的页框；分页是在建立虚拟地址到物理页框的翻译和权限。前一阶段的输出是后一阶段的输入，但它们不能合成一个“大内存模块”，否则格式错误、保留区冲突、页耗尽和映射错误会混在一起。

DTB 地址和 RAM 大小不能写死。QEMU 的内存参数会改变 RAM 范围和 DTB 放置位置，真实开发板还会有不同的固件保留区和设备布局。RISC-V 由 OpenSBI 在 `a1` 传入 DTB；未来 LoongArch 启动入口可以不同，但进入通用内存布局前也应先转换成明确的 RAM 与保留区事实。

## 为什么先做物理页分配，再做 Sv39？

页表本身也占物理页。若先写页表代码，它仍需要临时硬编码页表数组或地址，之后接入真正的页分配器时会重写所有权和失败路径。先完成物理页分配后，分页阶段可以直接表达“申请一页作为下一级页表；失败则回滚已经申请的页”，页表和普通内核页也遵守同一资源契约。

当前分配器消费已经排除保留区的 `usable[]`，把每段区间首尾向内对齐到完整页。初始化只保存区间游标；首次分配按地址递增，释放页则把页首 64 位作为侵入式回收链表节点。这一方案不会为了初始化扫描或写遍 QEMU 的全部 RAM。

曾考虑但没有选择的路线：

- 启动时把所有空闲页串成链表：实现直观，但会触碰每个空闲页，guest RAM 越大启动成本越高。
- 位图：查询和重复释放检查更稳定，但位图本身需要先找到、保留并映射元数据空间，当前启动阶段会引入额外的 bootstrap 问题。

当前“区间游标 + 回收链表”满足单 hart 和最小分页的需要。以后若连续多页、并发或大量回收使线性检查成为真实瓶颈，再以测量结果替换算法。

## 4 KiB、16 KiB 与三级页表是什么关系？

页大小是构建目标的基本不变量，不是运行时随意选择的参数：

| 目标 | 项目约定 | 当前状态 |
|---|---|---|
| RISC-V64（QEMU `virt`、VisionFive 2） | Sv39、4 KiB 基页、三级页表，`BOAROS_PAGE_SHIFT=12` | 物理页分配已实现，Sv39 尚未实现 |
| LoongArch64（2K1000LA 星云板） | 16 KiB 基页、三级页表，计划使用 `BOAROS_PAGE_SHIFT=14` | 构建目标和分页均尚未实现 |

Sv39 中“39”表示受规范约束的 39 位虚拟地址形式；4 KiB 基页留下 12 位页内偏移，其余虚拟页号由三级索引查找。三级页表不是“三种页大小”的同义词：叶子放在哪一级会决定是否形成大页，而项目第一版固定建立 4 KiB 映射，减少启动期变量。

物理页分配器只依赖构建期的页大小，因此算法可以复用；PTE 格式、页表遍历、启用分页的 CSR 和 TLB 刷新则必须留在各架构实现中。不能用一套 RISC-V PTE 代码假装支持 LoongArch。

## QEMU、开发板和架构差异怎样隔离？

隔离边界按“机制属于谁”判断：

| 层次 | 应隔离的内容 | 可复用内容 |
|---|---|---|
| 通用内存机制 | 可用区间、物理页所有权、通用映射意图和错误语义 | DTB 事实转换后的区间算法、物理页分配状态机 |
| 架构 | PTE 编码、页表级数细节、`satp` 或 LoongArch 控制寄存器、TLB 操作、物理地址到内核可访问地址的转换 | 对上提供最窄的建表和启用接口 |
| 平台/开发板 | 固件交接、RAM 与 MMIO 布局、UART、中断控制器、时钟、关机和设备树来源 | 同架构页表机制通常可复用 |

因此 RISC-V 侧的 Sv39/4 KiB 机制应在 QEMU `virt` 与 VisionFive 2 间复用，板级代码只处理各自的启动和设备事实。当前分页关闭，RISC-V 能以相同数值直接访问物理页；启用 Sv39 后必须保证分配器托管的 RAM 在内核地址空间中可访问。LoongArch 接入时需要按其地址窗口建立显式的物理地址转换，不能把当前的恒等访问假设泄漏进通用分配器。

在拿到开发板前可以完成并用 QEMU 验证架构机制和平台边界，但不能宣称真实板级适配已经完成。开发板阶段仍要用实际固件、DTB、RAM 保留区、UART 与启动方式验证这些假设。

## 当前做到哪里，下一步验证什么？

已经完成 DTB 读取、启动内存布局和单页物理分配；尚未创建 Sv39 页表，也没有写入 `satp`。下一阶段应在 RISC-V 上用物理页分配器申请页表页，建立启动所需的最小映射，切换 `satp` 并执行规定的 TLB 同步，再验证切换前后的 UART、栈、代码、DTB 和托管 RAM 都可访问。LoongArch 分页在 RISC-V 路径稳定后实现，届时复用通用物理页语义，不复用架构页表格式。

当前验证入口：

```sh
make test-dtb-riscv   # DTB 与字节区间布局
make test-page-riscv  # 物理页分配状态机
make test-riscv       # 上述聚焦测试和两种 RAM 大小的完整启动
```
