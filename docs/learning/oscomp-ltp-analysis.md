# 完整评测的得分、耗时与 LTP 能力分析

## 结论与结果范围

- 通用 ext4/VFS 修复属于 `main`：`74b85ac` 修正 extent 向左合并的物理起点和索引，`5273771` 修正截断与旧写回的交错；`267c1ad` 将它们单向合入 `oscomp-compat`。这两项均有先失败、后通过的确定性短复现。
- 原 scratch 获取失败同时包含环境缺失和内核能力缺口。本轮已在 main 实现块设备 OFD、常用 loop、真实 fallocate 和写入接纳回收，并在兼容分支配置独立 scratch、LTP_DEV 与目标架构 mkfs；当前机制及定向结果见下节。
- 原完整运行的两架构并行，每架构内按组和 libc 顺序执行。本轮目标验证同样使用独立可写盘，最多两台 QEMU 并行；各项的实际运行批次与代码版本见定向结果。
- LTP 之前已消耗约 47–48 分钟，其中 lmbench 占 42–44 分钟。3600 秒预算下只删除少数慢 LTP 项无法解决总时间问题。
- 原始 LTP 分数混合了真实语义检查、参数组合检查、前置检查以及旧输出格式差异，不能把得分比例当成整个 Linux ABI 的覆盖率。

### 计时的真实边界

最细可靠计时是**一次程序执行**。程序内部每条 TPASS/TFAIL 没有独立时间戳，不能把同一个父程序总时长复制成每条断言的实测耗时。原始观察器确实漏记了 632 个 LTP 项，后续用相同内核单独补测补齐；10688 项采用首轮时间，632 项采用补测值，来源保留，不能把补测值称为首轮实测。完整组时间线由两观察器 UTC 起点对齐，存在约秒级误差。

## scratch/loop：原失败与当前修复

原完整运行未提供 `LTP_DEV`，设备准备先生成后备文件，再查找空闲 loop。
每架构 128 个名字 × 两种 libc，共 256 次未能取得测试设备：252 次找不到 loop，
另 4 次为 fallocate06/fs_fill 更早准备失败。这些历史零分不能当作目标功能的语义失败。
原失败合计耗时 RV 30 分 23.3 秒、LA 18 分 40.8 秒，包含重复准备文件的 I/O。

| 层 | 原因 | 当前处理 |
|---|---|---|
| 启动环境 | 只有根盘，无独立可格式化设备、LTP_DEV 和完整 mkfs 工具 | 兼容分支的本地 make/run/debug/诊断入口共用准备逻辑；每架构独立 2 GiB、4 KiB ext4 scratch，PID1 核对设备身份后设置 LTP_DEV 及 ext4 限定 |
| 用户态块设备 | 只有内核内部 VirtIO I/O，块节点 open 和容量 ioctl 不可用 | main 提供实际设备引用、独立 block OFD、字节/向量/定位 I/O、容量/扇区/只读/同步 ioctl，以及挂载和独占 claim |

### fallocate06/fs_fill 的 ENOSYS 与 ENOMEM

两项均要求至少 1 GiB，而原输入盘空闲只有 RV 约 921 MiB、LA 约 669 MiB；
原根盘无法承担该 scratch 工作量。本轮在两架构的原程序准备路径记录实际调用后确认：

1. syscall 47 的 mode=0、offset=0、length=1 GiB 原先返回 ENOSYS。
2. helper 随后用 1 MiB write 循环回退。正短写不重设 errno，因此上一轮 ENOSYS
   可遗留在其报错中；它不表示最后一次 write 返回 ENOSYS。
3. 实际 ENOMEM 来自缓存页分配：可用页为 0，约 940–994 MiB 数据仍为脏页，
   当前写资格与分配器重入保护禁止在该层等待回收。它不是 helper 文本推测出的错误。

写入接纳现在保持整次 write 互斥，在 inode/用户页 pin 之前按窗口推进写回并回收。
写回在所属缓存执行者中使用预留工作区，既不在分配器锁内递归 I/O，也不让执行者等待自己。
错误仍记在实际 inode；另一文件的 ENOSPC/EIO 不污染当前覆盖写，正短写继续保留真实前缀。

定向压力检查以 16 MiB 页池写入 24 MiB，覆盖磁盘足够、磁盘满、真实无可回收页和写回 EIO，
以及其他 inode 失败后的独立写入，共 24 个几何/错误场景，均检查数据、错误、资源归还及 fsck。
fallocate 使用真实 unwritten extent；索引分割空间不足时初始化已有预留范围，不另要数据块。
释放块在即时和组提交 journal 中都保留到 abort/checkpoint 结束，避免事务回滚后旧数据被清零。

### 跨块组填盘的日志预算问题

原程序在真正进入满盘场景后，又暴露了小镜像回归没有覆盖的组初始化问题。
数据块分配与 inode 分配共用准备函数，首次进入 lazy 块组时，数据分配也清零整个
inode 表。2 GiB 文件系统每组 8192 个 256 字节 inode，表为 2 MiB；日志同时保存
前后版本，连同其余元数据超过 4 MiB 预算，失败后重试同一个无法容纳的操作。

单项 RV 原程序现场停在 `ext4_fs_init_inode_table(group=1)`，日志 budget_failures
已达 2443，而 accepted、sealed、durable、checkpoint 均停在 339，journal.error=0。
原 LTP 150 秒内部超时后，卸载因剩余脏页无法写回返回 EIO。后续程序仍清理同一设备，
原 `tst_clear_device()` 会先清零 512 KiB，随后 mkfs 才因设备占用而退出；因此混合失败
session 的最终坏主 superblock 来自这次后续清理，不能据此判定首次填盘覆盖了元数据。
仅运行一个原程序的诊断中，scratch 主 superblock 正常、只读 fsck 为 0，仍不能替代
正常卸载和完整写回通过。

分配准备现按实际用途初始化位图：数据分配不接管 inode 表；inode 分配初始化
需要的位图，并使用现有新 inode 槽清零及同事务的 itable_unused 更新。未清零整表时
保留 ITABLE_ZEROED 为假。main 修复为 `b80cd43`，单向集成到兼容分支 `bb6b49e`。回归显式关闭 discard 并启用 lazy inode table，避免宿主
格式化器提前清零表而漏测；覆盖跨三个物理块组的预留/写入，以及新组 inode 的创建。
8 组场景及回滚/OOM 检查通过，另对 106 个实际写入/flush 位置进行断电恢复，每份恢复镜像 fsck 正常。

### 满盘写入的空间保证

跨组初始化修复后，原 `fallocate06` 已能填满 2 GiB 设备，但在收到 write 的 ENOSPC 后，
紧接着的 `fsync` 仍报 ENOSPC。原因是原缓存写先向用户确认数据和 EOF，直到写回时才
分配物理块；其他写入用尽磁盘后，先前已确认的数据也无法落盘。现场一个已成功写入并
关闭的文件应有 83,614,042 字节，实际只落盘 53,739,520 字节。因此不能清掉写回错误、
丢弃已确认尾部或把 fsync 改成成功来迁就测例。

固定 Linux 用同一个原始 RV glibc ELF、同样的 2 GiB scratch 和空参数完成 8 条 TPASS，
另有 1 条 FS_NOCOW_FL 不支持的 TCONF，正常卸载及两盘 fsck=0。该程序遇 ENOSPC 后
主动 fsync、缩小剩余写量再重试；这是合理的满盘行为。本轮修复把空间保证移到接纳新数据
之前：后端准备物理映射，缓存只复制已准备的范围，不能准备的后缀产生短写或 ENOSPC。
shared mmap 的可写缺页也必须保证整段有效页的空间，再发布可写 PTE；私有 COW 不分配文件块。
真实设备或后端写回错误仍由原 owner 报告。main 的 `381c42c` 实现该接纳边界，
并补齐旧式 inode 未用尾部的回收、失败关闭后的重试对象和共享映射替换时的错误重查。
48 个不同的短复现场景检查已确认字节、磁盘满短写、来源错误、实际映射、资源归还和 fsck。
随后还需解决下述内存回收与日志配额问题，原程序才完整通过；最终结果统一见开头的定向表。

`fs_fill` 的两个细项分别使用向量顺序填盘和随机长度文件填盘；每项运行
`CPU 配置数 + 2` 个线程，反复填盘、删除一个文件并重试。`.max_runtime=300` 是名义运行预算，原框架内部
超时为330秒；源码在已有 ENOSPC 且计数循环到 1000 次，或 ENOSPC 超过 100 次时
结束控制循环，随后等待各 writer 真正退出。两种模式各自的通过结果和填盘进展共同说明
测试完成情况。原输出中的 `runtime ...ms` 是带 usleep 的循环计数，
实际程序耗时以外部单调时钟为准。对应固定版本源码为
[fs_fill.c](https://raw.githubusercontent.com/linux-test-project/ltp/20240524/testcases/kernel/fs/fs_fill/fs_fill.c)。

### fs_fill 的工作量、内核成本与优化

固定 LTP 20240524 的两个细项分别调用 `tst_fill_fs()` 的向量与随机文件路径。
`lib/tst_rand_data.c` 中缓冲长度为4096：向量路径一次 `writev` 放512段，即2MiB；
随机路径将0～100MiB的随机文件拆成至多4096字节的 `write`。单CPU配置有3名writer，

还包含文件创建、遇到ENOSPC后的 `fsync`／剩余长度减半重试，以及各线程最后的删除。

### 写回窗口与内存回收

原 RV/glibc `fallocate06` 在接纳修复后运行 53.495 秒，创建 `file25` 时的 open 返回 ENOMEM；
此时无新的文件系统损坏，正常退出、heap-live=0，根盘和 scratch 的 fsck 均为 0。
这与原先 fsync 无法持久化已确认数据是不同的问题。

统一 16 MiB 物理页池的短复现中，实际失败发生在后台写回将 unwritten 块初始化时：
`writeback_run → ext4_write_spans → jbd_trans_write_data → jbd_image_alloc` 申请 4 KiB 失败。
现场空闲页为 0，缓存占用约 3644 页，脏页约 286–319 页，堆仅约 338 页。
旧锁序阻止后端分配取得缓存遍历资格，而批间回收出的空闲页又会被其他写者消耗。
实际遍历只回收干净且无人借用的页，不调用后端；节点最终释放由 worker 另行处理。
因此修复按这项职责调整锁顺序，允许后端分配使用现有干净页回收，并等待短暂占用的
纯缓存元数据资格；持锁期间仍不等待脏页或设备 I/O，重入场景也不等待自身。

另一个反例发生在缓存索引扩容的 64 KiB 分配：空闲页总数足够，但没有连续的 16 页。
分配器原先只回收一批并重试一次；现在在每次实际归还页面后重新尝试所需连续块，
直到成功或没有回收进展，不能用空闲页总数代替连续块条件。main 的 `877471e`
实现这两处修复；16 组统一页池场景均完成创建、持久化、重新打开和完整内容检查，
其中 8 组持续写入 48 个 4 MiB 文件，另有 24 组真实内存/空间/设备错误检查。
RV/glibc 原 fallocate06 随后得到 8 TPASS、1 TCONF，fs_fill 两种模式均通过，正常退出和两盘 fsck=0。

### 创建文件的 journal 配额

LA 原始 fallocate06 在填盘途中创建文件返回 ENOMEM，是另一种分配失败。
只读断点现场显示物理空闲仍约 40 MiB，堆 allocation_failures=0；journal 的
memory_used=4,177,280、memory_cached=31,168、limit=4,194,304，budget_failures=518，
accepted/sealed/durable/checkpoint 为 971/970/969/969，journal.error=0。
断点位于 create 外层事务失败处理，最终原输出明确为 open ENOMEM；不能把这个错误
归为 LA 堆容量不足，也不能将正常配额检查的暂时拒绝全当作失败。

写入范围已有预算拒绝后的回滚、等待旧事务进展和重做处理，创建文件的完整原子操作需要
保留同样的责任。修复按完整 metadata 操作组织：只有本次真实配额拒绝、私有操作已回滚、
日志无错误且旧组能推进时才等待和重做；临时文件 handle 在重做前关闭、清空，VFS 对象
在最终事务成功后发布。真实物理 OOM、设备错误和单操作确实超出预算继续报告错误。
短复现在 4/16 KiB 页、1/4 KiB 块的四个组合上共制造 36 次真实预算拒绝，
八类目录操作和带外部 capability EA 的 chown 均在旧 checkpoint 推进后成功；
另有 16 个超预算、嵌套外层、真实 OOM 和设备 EIO 负例保留实际错误。
数据、权限、链接、已打开孤儿、chown 同步序号、资源归还与 fsck 均正常；
原有 ownership 检查另覆盖 112 个逐分配 OOM 位置和写入/flush 故障。
通用修复已提交 main `e44fdda`，单向合入兼容分支 `01e9704`；两架构、双 libc 原程序
现已完成，结果统一见前面的定向表。

### 一致性修复与短验证

- extent 向左合并曾只移动逻辑起点而未移动物理起点，导致物理块错配、位图失配及重复释放的
  EUCLEAN；main 的物理起点/索引修正解决这一共同原因。
- truncate 提前释放 inode 保护、尚未退休旧缓存版本，允许旧写回重建截掉的映射，是旧数据
  再出现的另一条具体路径；修复把尺寸发布、缓存退休和旧写回失效放在同一一致性边界。
- 正常卸载另发现 orphan 恢复在 journal worker 停止后接受新事务、等待无人推进的 checkpoint。
  现在先在 worker 存活时恢复 orphan，再 drain、停止并卸载；不把超时关机当成一致性通过。

main 的两架构并行短验证均完成真实 scratch 格式化、loop 格式化/挂载、写入、同步和读回，
RV 17.59 秒、LA 17.49 秒；正常关机，heap-live=0，根盘、scratch 与提取的 loop 文件系统
`e2fsck -fn` 全为 0。`d3de6ce` 的 raw block ABI 与固定 Linux 原生对照各 35/35 一致，
包括非对齐/向量/定位 I/O、坏指针、容量末尾、dup/fork 偏移、只读、独占及同步；双方根盘 fsck 正常。
宿主检查另覆盖两种页大小、两种文件系统块大小、真实两层 loop、私有 COW、活动写回、
失败回滚、满盘预留写入及持久化等待。机制见[VFS/ext4](../modules/vfs-ext4.md)。

### 有效能力与具体缺口

- **epoll 有真实就绪与等待能力，但 256 分不能解读成 256 种投递语义。**`epoll_ctl03` 对已注册 pipe FD 做 256 种事件位组合的 MOD 返回值检查；`epoll_wait01` 另有 3/3 个读写就绪检查。四种配置的 `epoll_ctl03` 合计 1024 分，占全部 LTP 原始分约 14.3%。
- **pipe11 的 70 分是实际内容检查。**它以 1/2/3/4/10/50 个子进程读取并核对管道长度与字节，再回收；四种配置合计 280 分。这与上面的参数组合检查含义不同。
- **futex 基础等待/唤醒可用。**例如 RV glibc 的 `futex_wait01` 为 4/4，`futex_wake01` 为 6/6；只覆盖这些超时、值不等和唤醒条件，不代表所有 futex 操作均实现。
- **目录创建标志已修复。**修复前 `open11` 为26/28，目录及指向目录的链接以 `O_RDONLY|O_CREAT` 打开被误接受；目录分支漏查 O_CREAT。main `8eff5ad` 已统一修复打开检查，当前官方原程序四组均28/28，见[定向结果](oscomp-official-delivery.md)。
- **CPU 计时器确实缺能力。**`getitimer01` 为 20/32；当前 `which=0` 的 REAL 路径可用，VIRTUAL/PROF 明确返回 ENOSYS。应按计时器种类描述，不能说整个接口全过或全无。
- **资源限制前置会挡住别的测试。**例如 `abort01`、部分 `shmat01` 在 RLIMIT_CORE 查询返回 EOPNOTSUPP 后被中止。缺口属于资源限制能力；未到达的目标功能不能再据这次结果判失败。
- **Kconfig 探测失败不证明目标功能缺失。**每架构 172 次相关零分项在解析 Linux `.config` 时退出；不能伪造配置骗过探测，也不能仅凭这批记录宣称每个目标 API 均不存在。
- **IPv4 零目的地址已修复。**修复前将 bind 得到的 `0.0.0.0` 用作目的地址时，导入路径原样交给 lwIP，约18秒后 ETIMEDOUT。main `8eff5ad` 已将连接/发送中的零目的地址按 Linux 处理为本机目的地，bind 继续保持通配地址；定向对照及原 connect01 的四组7项均通过。

这些事实说明：基础文件/管道/就绪通知/进程/信号已有大量可用行为；得分损失同时包含真实 ABI 缺口、前置准备失败、用户态运行库差异和输出协议差异。仅统计 TFAIL 数无法决定应该改哪个内核模块。

## lmbench 测什么，以及怎样缩短反馈

24 条原命令产生 36 个判分指标。它同时测内核入口与对象查找、进程与信号、MM、文件系统和 IPC；不只测磁盘速度。

| 命令家族 | 对应能力 |
|---|---|
| lat_syscall / lat_select | syscall 入口、读写、路径 stat 与 fd fstat、open/close、100 FD 扫描 |
| lat_sig | 信号安装、递送/返回，以及保护故障到信号处理 |
| lat_pipe / lat_ctx | 管道往返、阻塞唤醒和多进程交接；lat_ctx 还包含每进程 32 KiB 工作集，不是只量汇编 context switch |
| lat_proc | fork/COW/退出回收、exec/ELF、shell 启动 |
| lat_pagefault / lat_mmap | 文件映射缺页和映射生命周期；一次文件缺页不必等于一次物理磁盘读 |
| lat_fs / lmdd | 文件创建删除、目录/元数据/回收、含同步的文件写 |
| bw_pipe / bw_file_rd / bw_mmap_rd | 管道、普通读和 mmap 读的吞吐；open2close 项还包含建立/关闭映射或文件的成本 |

### 得分与整条命令耗时的关系

原 judge 对有效指标先计算比值 `r`：延迟用“基准 / 实测”，吞吐用“实测 / 基准”。
无有效值为 0 分；`0 < r < 1` 为 1 分；`r ≥ 1` 为 `2 − 1/r` 分。
**整条命令的墙钟耗时不直接参与判分。**因此某项即使加速，只要仍低于基准，
分数可能仍为 1；总预算耗尽导致后项没执行，才会间接失分。本轮保留原参数、采样和 judge，
没有通过减少迭代来换取更短的正式时间。实现依据为固定输入的
[judge_lmbench-glibc.py](../../references/oscomp-autotest/kernel/judge/judge_lmbench-glibc.py)。

### 为什么每条命令会跑几十秒

计时库默认 `TRIES=11`，每个进程自动寻找 5/10/50/100 ms 采样窗口，并用 0.25% 线性误差要求检查；校准失败会退到 1 秒。每条新进程重新校准。`lat_fs` 又对 0/1/4/10 KiB 文件分别做创建、删除，共 8 组 benchmp；`lat_ctx` 包含开销测量和 8 种进程数。

已有相同内核的独立命令补测中：LA lat_fs 两种 libc 分别约 297/310 秒，lat_ctx 各约 138–139 秒；RV lat_fs 约 74 秒（glibc），lat_ctx 约 139–143 秒。它们来自补测，不能当作首轮逐命令时长。原完整 glibc 的文件操作速率反而是 LA 高于 RV（空文件创建 1309 vs 1104 次/秒、删除 479 vs 362 次/秒），所以不能把 LA 的 lat_fs 命令墙钟更长解释成文件系统慢四倍。

同一轮 glibc 的 stat/fstat 为 RV 130.3/11.2 μs、LA 107.8/9.5 μs，提示应关注路径解析、目录查找及权限/元数据取得的额外工作；它不是单凭墙钟就认定块设备慢的依据。对这些路径的修改仍须保持同参数和相同完成条件进行比较。

**缩短日常反馈：**按正在修改的能力选择原命令；若降低 `-N` 或指定较小 `ENOUGH`，明确作为快速诊断，失去原采样条件，不能当正式同参数成绩。**改善正式测量：**减少真实路径成本可以改善 μs/吞吐指标，但自校准可能增加迭代次数，整组墙钟不一定同比缩短。当前没有这两处一致性修复带来的 lmbench 配对加速数据。

## 3600 秒应如何决策

原顺序下留给 LTP 的预算只有 RV 约 759 秒、LA 约 690 秒。已有程序级时间离线估算表明：

- 只排除 netstress 与 shm_test，整次仍约 RV 149.8 分钟、LA 133.6 分钟。
- 排除本轮全部 scratch 失败名字，整次仍约 RV 134.4 分钟、LA 134.9 分钟。
- 排除所有配置都为零分且某次超过 10 秒的 31 个名字，整次仍约 RV 124.2 分钟、LA 110.6 分钟。
- 即使按本轮结果事后删去所有零分名字，保留全部本轮正分，仍约 RV 75.3 分钟、LA 76.0 分钟。再删 starvation/mmap1 会各损失 4 个原始分，模型仍约 3615/3653 秒，没有可靠余量。

这些只是**修复前工作量的离线模型**，不是实际 3600 秒重跑结果；跳过准备失败项也会改变 I/O 和后续资源状态，修复后原程序能完成更多工作，耗时可能变化。“历史零分”不能作为永久排除能力测试的理由。

优先顺序应为：先解决可达性和测量含义（块设备 ABI/独立盘、工具/解释器/账户、真实熵、正确控制器调用），保留内核语义失败用于短复现；日常按能力选测。若正式仍要求原脚本和原参数，则预算与排除项需作为明确取舍，不能把缩小 lmbench 工作量伪装成内核加速。
