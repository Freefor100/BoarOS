# OSComp iozone 分项与性能分析

本页统一维护iozone的实际覆盖、原judge分数、逐方法吞吐和相关性能原因。当前记录为2026年10月30日，从10月29日19:23批量借用版到10月30日17:16时间戳修正版。策略原型未进入生产分支。

## 原因定位与优化方向

这组修改没有显著改变完整原版 iozone 的本地计分结果。主要诊断进展是：大文件写回的批量提交确实被切碎，但恢复批量后尚未得到稳定吞吐收益；相比之下，扩大 journal 内存额度的受控原型同时减少了 checkpoint 等待、封组和 FLUSH，并改善了包含最终 fsync 的追加写。下一步应先整理 journal 额度不足时的资源归还责任和等待目标，再决定默认内存额度与 phase 窗口。

完整运行覆盖六个提交阶段、RV/LA 各八次启动、256条原命令；端点各复跑两次，中间阶段各一次。条件为单核、512MiB、ext4 4KiB块，原版ELF与loader不变，关闭内核诊断计时。工作盘在整个consumer运行期间只挂载一次，两种libc共用这一挂载，musl先于glibc；各命令之间保留这一挂载及其运行时状态。分数来自本地重放原judge及其整数投影，并非比赛平台正式运行。带`-C`的顺序诊断、COST观察、ptrace跟踪和策略原型另列，不进入完整原命令计分。原ELF的`(11,12)`选择不可用，其实际回退写结果仍按原judge计分；vector I/O能力由单独ABI测例验证。[完整结果](/home/leo/BoarOS/build/io-investigation-20261030/full-results.md)、[覆盖与计分口径](/home/leo/BoarOS/build/io-investigation-20261030/coverage.md)

完整端点浮点合计为 **140.1842→140.7002 /160**，增加0.5160分、约0.37%；端点两轮的原后处理整数投影均为140。RV合计67.2876→67.7237，LA合计72.8966→72.9765。原judge只取最快子进程的吞吐，默认写方法在自身计时结束后才fsync；最终同步更慢时，Max分数仍可能几乎不变。Parent、实际传输量、最终同步和完整退出时间需要保留各自含义，完整I/O判断同时检查这些指标。

**journal额度与等待目标是目前证据最强的优化方向。** 在latest的LA、16MiB文件/64KiB记录、`-i 0 -i 1 -i 2 -e`观察中，每种libc都完成48MiB写回，均有13次前景checkpoint等待，累计约312.5/320.5ms；memory/log/resource重试均为零。journal当前预算为`min(可管理内存/32, 4MiB)`；19:23版已采用同一上限；本次latest观察确认该额度参与checkpoint等待和额外封组，旧版流水形态下的占比仍需分别测量。观察到的内存峰值最大值为4,145,408/4,167,040字节，即3.95/3.97MiB。`journal_memory_peak.value`是各次观测之和，应以`.max`解释峰值。[COST原始快照](/home/leo/BoarOS/build/io-investigation-20261030/observe-la/la-latest-cost-observe/console.log)

这里的commit与checkpoint承担不同任务。commit先让文件数据与日志内容持久化，再写入并同步提交记录；掉电后可据日志恢复，fsync所等的durable目标至此满足。checkpoint随后把已提交metadata写回正式位置，再同步journal头部，归还日志空间和旧metadata owner。借给journal的稳定文件数据在commit完成时已经归还，不必随metadata一起等到checkpoint。

当前`ext4_write_spans`、写空间准备和`trans_start`都调用`jbd_journal_operation_room`检查额度。检查只有“够/不够”结果，不足时统一选择checkpoint目标；这类正常的接纳前等待不会增加memory/log重试计数。因此零重试不能排除本次已经看到的预算压力。下一步应让额度不足的原因保留到等待目标选择：借用文件数据占满额度时，推动能释放这些数据的commit；metadata、日志空间或已释放块复用受限时，等待相应checkpoint。等待目标必须与资源来源一同修改：当前reclaim目标优先取最老的checkpoint队列成员，它可能已经durable，直接替换会立即返回而没有释放所需资源。[调用与所有权路径](/home/leo/BoarOS/build/io-investigation-20261030/policy-paths.md)

持久化屏障应继续按实际责任保留：每个commit有两次FLUSH，每个checkpoint批次也有两次FLUSH，并非每组固定三次。4MiB观察中的musl，device1有18组commit和15批checkpoint，`18×2+15×2=66`；root盘另有2组commit，合起来才是全局20组。glibc的device1为19组commit、16批checkpoint，`19×2+16×2=70`。减少无必要封组、选择能够归还资源的完成阶段，可以减少屏障次数；所需屏障保持不变。

**优化判断。** 本批最有力的方向是journal额度原因与资源归还阶段的对应关系：4 MiB上限下已经观察到反复等待，扩大预算的反例同时减少等待与同步并改善含同步吞吐。按实际可归还的资源选择等待目标，有望在保留额度约束的同时降低串行成本。full-phase和1 MiB窗口已证明可恢复合并，但应用吞吐收益未稳定，仍作为实验记录。上述原型均保存在忽略目录，生产配置保持原样。

## 覆盖与评分

每种libc执行八条原命令；两种libc共16条。自动模式给出13个方法的吞吐，原judge只为后七条命令产生的20个Max结果计分。请求向量方法的最后一条在原ELF中不可用，实际回退为两项普通写；原judge仍对它们计分。

## 六阶段完整结果

完成 RV、LA 各八次串行启动，共 256 条原命令正常退出。每次均运行两种 libc 的自动模式及七组四进程命令；32 条 `(11,12)` 选择被原版 ELF 明确报告为不支持，其实际回退写结果仍按原 judge 计分。

条件为单核 UP、512 MiB、ext4 4 KiB 块；每架构各阶段共用相同输入模板、原版 ELF/loader 和同一个 consumer，运行盘独立复制。vCPU 固定宿主 CPU2，主线程与 I/O 固定 CPU8，计时关闭内核诊断。每条命令预算 120 秒。

每架构顺序均为：批量借用版 → 扩额版 → 顺序读版 → 静态配额版 → 动态配额版 → 最新版 → 批量借用版复跑 → 最新版复跑。端点各两次，中间四阶段各一次。下文端点取两次中位数，中间阶段保留单次观测；它们用于观察阶段变化，不代表已稳定分离每个机制的贡献。
