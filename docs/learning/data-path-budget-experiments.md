# 数据路径实验

## RV ext4 目录与路径在调用 CPU 执行（2026-10-20）

本节记录 2026-10-20 的目录本地化对照：ext4 路径查找、打开、目录读取、创建、删除、改名及普通对象最终关闭已由发起任务执行，当时同一挂载串行修改目录和事务。journal/checkpoint、后台写回与挂载管理由 CPU0 推进。当前按对象并行准备事务的机制和执行边界见 [VFS](../modules/vfs-ext4.md) 与 [RV SMP](../modules/riscv-smp.md)。

**本轮中位数目标达成：受影响的单核负载和双核共享目录均在目录改造前 +3% 以内，
相对本轮起点的已有加速项目也均在 +3% 以内。** 单核 fstat 为 +1.51%，其余单核目录
负载快 10.08%～74.25%；单核热读、追加加 fsync 分别为 −0.19%、−0.46%。
双核共享目录为 3547.097→2738.149 ms，比目录改造前的 2766.599 ms 快 1.03%。
下表区分目录改造前、本轮起点和最终内核；此前 +3%～10%／+26.77% 的原批记录保留在
`build/namespace-stage/`，本轮结果采用新的四版本对照。

### 具体成本与实现

| 实际执行链 | 重复或额外工作 | 当前处理 |
|---|---|---|
| 普通文件 O_CREAT | 首次查找失败后重新解析、再次分配 OFD | 一次请求返回已有目标或带引用的父目录与名称，普通文件 OFD 分配一次 |
| 同挂载路径操作 | 各分量和最终修改反复取得同一 namespace，双核可反复 park/IPI/恢复 | 一次操作保留一份挂载资格，lookup 使用已有资格，跨挂载时交接实际引用 |
| 普通路径及 rename 父路径 | 每次分配并复制 8 KiB 展开区；rename 另复制父路径 | 借用调用者不可变文本；文本符号链接首次展开才分配；父路径用有界前缀 |
| fd 属性查询 | 执行范围选择和旧页缓存回调重复承担递送 | 在产生内核 stat 时按后端选择执行位置，随后复制用户结果 |
| RAM 复制和 CRC | 源/目标页或输入/表页交替；每四字节更新一次 CRC 状态 | 复制先读四字再写；CRC slicing-by-8，一批先读四个 64 位输入 |

原 O_CREAT 尾斜杠与 proc 管道链接的错误也按 Linux 对照修正：前者返回 EISDIR，
缺失父路径仍先报父路径错误；后者通过真实 OFD 重开，不把展示文本当创建路径。
O_EXCL、悬空链接、只读挂载及已有目录的顺序均有原始 syscall 对照。
root/cwd、dirfd、路径和 inode 继续持有真实引用；目录修改成功后再发布名称与父边。
既有闲置块缓存计数、日志预算回滚和实例等待队列机制沿用 [VFS](../modules/vfs-ext4.md)。

审查发现对象链接的一条跨挂载清理交错：CPU0 取得目标 OFD pin 后，CPU1 归还原 owner，
CPU0 返回目标路径时释放最后 pin；若文件已经 unlink，关闭会取得目标挂载的 namespace。
解析器若仍持 proc namespace，就会触发同 rank 锁顺序断言。
现在跟随和读取链接先归还 namespace，保留链接 inode 的真实引用，再取得目标引用；
返回后为实际目标重新取得保护。宿主双 CPU 握手反例在修复前触发断言，修复后的
follow/readlink 两类交错均保留正确身份，最终归还两个挂载、路径及 OFD。

### 数据访问、翻译块与指令计数

实际 QEMU 二进制的只读 GDB 快照捕获到：内核栈窗口页 `0xffffffffc0008000` 与直接映射页
`0xffffffc0bfe08000` 争用软件 TLB 第 8 槽；另有 bitmap 页 `0xffffffc0bfea8000`
与旧 CRC 表页 `0xffffffff800a8000` 争用第 168 槽。
复制按四字批次安排源读取与目标写入。CRC 每八字节得到一次新状态，
查表索引可以从旧状态和本批输入直接计算；四张新增表使只读表从 4 KiB 增至 8 KiB。
raw inode 查询直接复制实际磁盘前缀，只清零缺失后缀，保留每次真实 inode 校验。

计数来自独立诊断启动，正式耗时来自关闭诊断的后续表格：

总计1024次范围调用，最终一次fsync；它没有用户数据传输，速率按范围调用数/秒计算。

读窗口包含逐块内容核对，写窗口包含数据填充；写后完整读回和结果输出在窗口外。
追加的终点包括成功fsync；双进程以两个成功fsync的较晚完成为终点，
`sync_ns`仅表示最后数据完成后的同步尾部，各进程完整fsync区间另存。
单次请求延迟包含执行和等待；范围样本覆盖一轮四次系统调用。

### 执行位置、原因与边界

直接RV原生检查观察到CPU1执行空间准备、截断、三种fallocate和两次同步准备，
并在CPU1提交前台块请求；journal/checkpoint与后台写回仍由CPU0执行。
追加和范围操作减少了每次准备工作交给CPU0、等待完成后回到原任务的调度与通知；
后端写锁与单个活跃事务保持原有互斥，空间修改使用真实inode资格。
这解释了双核写路径的收益；同一挂载的元数据事务仍串行，目录本地化与四核是后续步骤。

复核修复了两处真实寿命问题：时间戳直接借句柄已有inode owner，
共享退休页的最终节点清理由现有CPU0 worker执行。窄反例分别触发旧的远端索引查找、
远端最后引用释放；修复后以明确握手覆盖更新时间时CPU0关闭另一inode，最终引用和资源归还正确。

最终源码完成RV 1/2核、512 MiB/1 GiB的新盘/重启，静态和动态musl的Linux／普通／受控组合，
两架构59项FSIZE对照、四种页/块几何的缓存并发、八种journal/nonjournal范围与CPU1打洞／活动写回检查。
兼容分支的原程序结果、32/36得分及八次分区检查由 `oscomp-compat` 的
`docs/learning/oscomp-official-delivery.md` 维护。
最终RV的CRC布局检查通过，UP/SMP的198字节函数分别位于
`0xffffffff80080300`／`0xffffffff80083800`，均在单个4 KiB代码页内。

### 单核开销从哪里来

初版在共用 I/O 路径加入了共享对象保护，默认单核构建也经过这些操作。
首次配对结果中，单核 4/64 KiB 冷读耗时增加 7.54%/5.11%，追加加 fsync 增加 7.35%。
本轮沿实际调用链删除重复工作，并让保护方式匹配访问者：

| 路径 | 初版额外工作 | 当前处理 |
|---|---|---|
| 缓冲命中 | 取得引用、选择装入者、检查结果分三次保护 | 取得引用时一次确定 READY/LOAD/WAIT；生产者直接发布结果，实际等待者才复查 |
| 默认 UP 短保护 | 维护完整 raw 持有链，并反复关中断 | 任务元数据只禁止抢占；设备共享状态再关中断，SMP/debug 保留完整 raw |
| 空闲缓冲顺序 | 每次首次借出、末次归还删除／插入年龄红黑树 | 按末次归还顺序维护双向队列，摘链、接尾、取最旧均为 O(1) |
| 干净引用归还 | 每次查询任务的后端读上下文 | 只在确有脏块立即刷回决策时查询 |
| 冷请求寿命归还 | 再获取一次缓存 mutex，仅将借用数减一 | 结束时 release 原子归还，销毁 acquire 观察零；接纳和 entry 发布沿原保护完成 |

直接反例中，热块标量／八块读取的保护次数由 **3/24 降为 1/8**；
九次干净归还的上下文查询由 **9 降为 0**；冷单页／八页请求的缓存保护次数由
**5/7 降为 4/6**。热页路径仍为一次缓存保护。旧年龄计数在 32 位回绕后会先淘汰刚归还的块，
双向队列同时消除了该顺序错误。分配、设备 I/O 与等待继续在短保护外，
重叠批次先发布自己的装入结果，再等待其他生产者。

### 写入验证中发现的 CRC 代码页问题

中间构建 `947bd0f` 的双核追加加 fsync 从初版 1544.773 ms 增至 1944.354 ms。
定位到 `ext4_crc32.c`：198 字节的 `crc32c` 被链接到 `0xffffffff80082fa8`，
每处理四字节执行的热循环覆盖 `0xffffffff80082ff2` 至 `0xffffffff80083038`，末尾跳回起点，跨过 4 KiB 指令页。
QEMU 的 `translator_use_goto_tb()` 只对同页目的地址直接连接翻译块，循环跨页后反复执行查找。
固定源码依据为 `references/qemu/accel/tcg/translator.c`。

在同一 ELF 的追加窗口内，CRC 的翻译块执行数由 **11,617,289 增到 33,401,859**，
按块统计的指令工作量分别为 286,723,453 和 286,739,933。
RV 将该小函数按 256 字节对齐后，函数位于 `0xffffffff80083000`，上述两个计数
恢复为 **11,617,289 / 286,723,453**。独立逐位校验和真实镜像检查通过。
该计数用于解释模拟器开销；正式耗时取下面关闭诊断后的整组对照。

## CPU0 分批推进与调用者持久化等待（2026-10-17）

### 回退的具体来源

逐提交对照与 QEMU 自带 hotblocks 插件发现，代码位置改变会影响短循环的翻译块划分。追加写中的前向 `memmove` 循环跨过代码页，复制指令量基本相同，却增加约 52 万次翻译块执行。另一处是 `kernel_lock_release` 的一条四字节 ANDI 指令横跨代码页，短指令序列由一个翻译块拆成三个，16 MiB 追加累计多执行约 13.5 万个翻译块。

`memcpy`、`memmove` 继续在各自入口内联同一份前向复制源码，分别按 1/2 KiB 对齐；短于 1 KiB 的锁释放函数也按 1 KiB 对齐。当前 RV/LA 函数体均落在各自对齐范围内，填充位于入口之前，不增加执行指令，也没有转发调用、额外零长检查或复制副本。该结果解释 QEMU 下的链接布局敏感性，不换算为真机加速比例。

64 KiB 冷读仍是 256 个 64 KiB SG 数据请求。原来的目标缓冲区检查每批比较 120 对地址；lwext4 与块层现在先比较已见地址边界，顺序 SG 目标使用线性检查，目标进入间隙时才逐项检查。另两项新增工作也已删除：同步 DMA 排空后逐页进入提前发布函数，以及结果检查、输出填写分别查询同一页的有效长度。排空后统一归并未消费片段，每页长度只取一次。实际尚有 DMA 或下一规划窗口时，继续提前发布完整页，保留生产者借用和真实错误前缀。

带设备跟踪的三轮对照中，各版本读取期间的数据请求量相同，均有时间戳元数据写入。单独给目标 inode 设置 NOATIME 后仍出现版本差异，后台时间戳等待不足以解释冷读回退；该诊断条件没有用于下面正式数字。

### 四进程 Parent read 的含义

原 iozone 3.506 在第一个子进程完成后通知其他读者停止。Parent 的分子是实际计入的传输量，区间结束于全部子进程退出；每个 reader 在结束自己的读取计时后还执行 fsync 和 close。因此 Parent 同时受读取速度、起跑分布、提前停止量及收尾持久化影响，不能用 Children 速率之和替代。`-C` 只增加子进程明细，`-x` 才关闭提前停止。来源为[原版 3.506 源码](https://www.iozone.org/src/current/iozone3_506.tar)；旧版宿主稀疏镜像问题及已落实的写实准备见 [VFS/ext4](../modules/vfs-ext4.md)。

原程序还用零 FD 的 select 实现短等待。过去 ppoll/pselect 无条件进入 CPU0 服务，连只涉及当前任务超时的等待也迁移；libc 的 pselect argpack 即使非空，其内部掩码指针也可能为空。现在按实际 FD 数和解包后的掩码决定：零 FD、不替换掩码时留在调用 CPU，真实 FD 或信号掩码业务仍进入原有服务范围。

默认仍为 8/1/1；随后网络默认改为 8/4/2，当时存储保持 RA0/WB1。下面表格
描述当时的数据路径；当前文件版本、SG 与写回结构见 [VFS/ext4](../modules/vfs-ext4.md#当前成本边界)，
不能把旧参数比较直接当作新实现的结果。

TCP 候选为 `w8/16/32-p1/2/4-m1/2/4` 共 27 组：窗口与发送缓冲为 8/16/32 MSS，
segment/pbuf 池及协议堆各自为 1/2/4 倍。PCB 数不变，32 MSS=46720 B，不启用窗口扩大。
存储为 `ra0/1/2/4/8-wb1/2/4/8` 共 20 组，实验时预读/连续写回默认 0/1。配置校验
拒绝其他数值；候选由独立 BUILD_DIR 构建，不覆盖根 kernel-rv。

`tests/network-budget-experiment.py`、`tests/io-budget-experiment.py` 与共享

源码身份绑定进 ELF 的非 ALLOC section，再记录最终 kernel SHA-256。运行同时核对
相邻 identity.json、ELF 内身份和真实文件摘要；canonical 标签必须匹配实际 profile，
`current` 只作显示别名。参数候选须来自同一保守源码集合（含未跟踪、非忽略输入），
整个 build 批次期间不得变动。运行时树身份与构建身份分开；固定旧基线和固定 Linux
明确作为例外，不猜测任意内核的配置。烟测可显式使用 unmanaged 普通标签，但不能
升格成正式性能；formal run 必须使用 managed 候选。

原基线为 `5687377c58dc96adfa1f72f1636a319bbd25b419`，本地复用缓存
`build/data-path-baselines/5687377/kernel-rv`，固定 SHA-256
`b962c890989d268282b55d49a4fa9b51afbaf7008dab2fc47e717388a6fea2f4`。
两工具支持 `--baseline` 指定同一摘要的文件，缺失或不匹配直接失败；不拿新构建冒充
该历史输入。可重建工作负载和内核源码均在 Git，缓存内核只是跨实验复用输入。

正式 release 至少三次独立启动，按 case/重复/variant 交错。每个 case 共用相同
ELF、初始镜像、QEMU、RAM、设备配置与缓存准备；每次启动复制磁盘。原基线自动加入，
Linux 只可通过 `--linux-kernel` 的固定源码/配置身份核验加入，保留 linux 标签。
TCP 与 I/O 的正式/诊断运行都取得 `build/cost/measurement.lock`；冲突先于构建或
启动客体被拒绝。该锁只约束合作工具，测量期间仍须停止其他编译/QEMU负载。
失败组标 incomplete，成功子集可保留诊断数据，但只有 status=measured 能用于比较。

## 负载与统计口径

网络 `all` 是 60 个明确 case：loopback/TAP、blocking/nonblocking、bulk/RR/mixed、
单/五/近池连接及方向。mixed 加一条独立控制连接，近池为 loopback 13 bulk+1 control、
TAP 27 bulk+1 control，留四个 active PCB 槽；这是 fixture 配额，不是协议优先级预留。
接收侧逐字节核对并确认全部连接完成，保存每连接起止时间和有效字节。准备阶段测
16 次 echo RTT；Jain 指标只描述有限完成速率，不作为长期无饥饿证明。
控制 tail 的主集合按 RR **发起时 bulk 尚活跃**选择，跨 bulk 结束的慢回复仍计入；
全部样本和 fully-contained 辅助集合另存，保留样本数，不按完成时点筛掉最慢请求。

loopback 的连接就绪与 RTT 预热完成使用两条独立放行管道。首次扩大验证在固定
Linux 的 blocking/RR/5 连接遇到 180 秒 workload timeout，结果文件为空；旧程序
两轮共用一条 gate，快客户端可能把慢客户端的第一轮 token 当成第二轮放行。
新增实际 workload 的宿主到达偏斜测试，旧代码稳定报告跨轮消费并停滞；分离后
通过。这里修改的是测量协调器，未改内核协议路径；新 workload ELF 必须与基线
重新匹配，旧失败批次标 incomplete，不混合两版 ELF 的吞吐或观测开销。

TAP 可选 `--tap-delay-ms 0/1/10`，只在隔离 namespace 的 host→guest egress 设置
netem，另报告实际 RTT。本宿主 1/10 ms 均返回 `Specified qdisc kind is unknown`，
在 QEMU 启动前明确记 unsupported。没有加载宿主模块或用另一种 relay 混作同一测量后端。
固定 ABI Linux 未启用 NETDEVICES，TAP 配置实测 ENODEV 后，另用既有
`tests/network-linux.config` 从固定 `references/linux@f4cdf7ca9a1fdcca413157df19753f388a5a224e`
构建网卡参考 Image（SHA-256 `7fdeac1a0821f821e02c15c35cd2c4003b66268a65b8ef591520094c096f442e`），
同 ELF loopback/TAP 功能已通过；原 ABI 参考保留。

存储 case 为 `backend:operation:completion:files:size:request`：ext4/tmpfs，
append/overwrite/cold-read/hot-read，1/4 个文件，每文件 1/4/16/64 MiB，请求 1/4/64 KiB。
overwrite 使用镜像已有文件且不 truncate；cold-read 是新 guest 首次读取预置文件，
hot-read 先完整验证读取一次。tmpfs read 是已建立的内存后备，拒绝 cold-disk 标签。
多文件由单任务逐请求轮转，不冒充并发调度公平性。cache 窗口没有显式 sync，fsync/
fdatasync 窗口在全部数据请求后每文件调用一次。setup、最后读回、cache 模式收尾同步
与结果文件持久化在主窗口外；模式生成、读校验及五个文件大小检查在主窗口内。
新 guest 缓存不表示冷宿主存储；tmpfs 同步成功不表示持久介质保证。

结果在传输/成本窗口结束后写客体文件并 fsync，退出后复制磁盘，只在读出副本重放
journal 再提取，保存原盘/读出盘/结果摘要。这样不依赖可能双向交错的串口记录。
COST 诊断另保存完整成本快照、32 位协议计数和协议池高水位；MEM_AFTER 仅为时点。
managed/heap peak 从初始化累计到查询前，排除未受管的内核映像/固件/MMIO，heap
为子集不可相加；不宣称 workload 独占峰值。release 与诊断扰动单独比较。

TX 诊断补充软件收割 DONE→FREE 和同槽 FREE→下一次 publish 的 count/sum/max，
单位由 `tx-clock-hz` 转换。范围是设备生命期，含准备和收口；后者也含正常空闲，
不能单独作为进展缺陷证据。复制 TX 的完成直接归还计零，首次使用和 reset-only
撤销不伪造完成时间。受控时钟测试先在缺记录实现上失败，补齐后两传输及 COST
开/关的实际驱动模型、worker 进展模型和结果解析测试通过。

### 参数建议与未验证边界

- 缓存追加占主导、尤其小请求：保持 WB1；64 MiB 的 WB8 回退不能忽略。
- 顺序冷读占主导：RA8 值得在目标数据集继续验证；RA1 没有普遍收益。显式同步写占主导时 WB8 的收益更明确；同时需要两类负载可试 RA8/WB8。纯预读失败仍不污染无关 demand 或写回错误 owner。
- 接近连接池上限且重视控制尾延迟：本次优先候选为 `w8-p4-m2`，它增加全局资源而保留小窗口；五连接 bulk 优先的应用可另评估 `w16-p2-m2`。32 MSS 不是通用推荐，更多池/堆也未单调提高收益。
- 实验结束时 TCP 默认为 8 MSS、1 倍池/堆；随后用户批准 8/4/2。存储仍为 RA0/WB1，不因某一种同步负载更快而统一增大预读/写回。
- 只测本机 QEMU 11.1.1、单 hart、512 MiB、modern VirtIO、固定 ELF/数据集及当前主机条件。legacy 的正确性另有门禁，此处没有对应吞吐分布。echo RTT 来自 16 次 64 B 应用请求，包含端点处理与调度，不等同于 TCP 内部 SRTT。1/10 ms netem 在创建 qdisc 时被拒绝，未启动客体；没有受控 RTT 收益结论。
- 三次范围不是充分统计置信度，也不支持实板、SMP、无限并发、长期无饥饿、所有 libc 应用或完整比赛 Harness 的结论。默认网络预算在若干吞吐负载的回退，以及全局协议资源失败后的重复复制，继续作为真实优化输入保留。
